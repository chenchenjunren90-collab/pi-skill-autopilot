# 设计笔记

这个插件为什么长这样，以及一路否掉了哪些方案。

如果只看一节，看[「评估候选」](#评估候选最要紧的一节)。

---

## 问题

用户让 agent 把一个 PDF 报告变成结构化工作簿加图表。做到一半，agent 发现它没有 PDF 表格提取、也没有图表工具。通常会发生三件事之一：

1. 写 200 行脆弱的 `pdfplumber` 胶水，勉强能用；
2. 告诉你这个能力不可用；
3. 装了个东西——经常是静默装、经常装错。

与此同时，商店里就躺着正好能用的技能。缺的不是能力，是**发现加上同意**：没有任何东西把"这个任务需要 X"和"X 只差一次安装"连起来，并且连在一个人类能说"可以"的时刻。

### 为什么不做成 skill

skill 是模型判断"相关"时才加载的 Markdown。它做不到：

- 观察每一次用户输入；
- 调用安装器；
- 往一轮运行里注入消息；
- 跨轮持有状态。

所以 skill 只能**描述**流程。这个问题需要**执行**——必须是扩展。

### 为什么不做自动安装

最直觉的产品答案是"直接自动装"。这不可接受，而且不是因为实现风险：装上的技能是一份 agent 被要求遵循的 `SKILL.md`，外加可选脚本。安装它本身就是一次信任行为。靠一个启发式规则静默安装，意味着这台机器可以被陌生人的文本牵着走，而操作者从没见过那份文本。

早期版本确实这么干过——用相关度阈值加黑名单兜底。它能跑通，演示效果很好，然后我把它删了。因为它装了用户不想要的东西的那一刻，省下的时间毫无意义。

所以：**代码里不存在静默安装这个模式**。不是默认关闭，是不存在。`auto` 在配置加载层被拒绝并迁移为 `confirm`。

### 为什么选计划时刻

输入时刻匹配有个根本缺陷：等你匹配用户那句话时，agent 已经选定做法了。

计划时刻不一样：

| | 输入时刻 | 计划时刻 |
|---|---|---|
| 工作被枚举 | 否 | 是，作为步骤 |
| 能力是具体的 | "拿这个 PDF 做点什么" | "提取表格"、"画图表" |
| 还没执行 | 通常不是 | 是 |
| 一个对话框能覆盖全部 | 否 | 是 |

模型写出计划，就等于刚刚告诉你它打算做什么。这是可获得的最高质量信号，而且是免费的。

因此三个触发器汇入同一条流水线：

1. 助手消息里的 `Plan:` / `计划：`（`turn_end`）
2. 传给计划/目标工具的结构化步骤（`tool_result`）
3. 写到磁盘上的计划文件（`tool_result`）

第 2 个是刻意做成通用的——提取器遍历工具入参，找字符串数组、或带 `title`/`text`/`task` 字段的对象数组，再从长文本里抽编号步骤。它不是工具名白名单，因为白名单会腐烂。`planToolPattern`（默认 `plan|goal|task|todo`）可配置，只读的 `get_*` 工具会被跳过。

## 评估候选（最要紧的一节）

拿到步骤之后要回答：*商店里哪个技能能满足这一步，值不值得装？*

诱人的答案是"问模型"。这是错的，三个理由：

1. **成本与延迟随候选数增长。** 五步计划对十个候选就是五十次判断，每次计划都来一遍。
2. **不可复现。** 同一个计划跑两次两个答案，而且两个都没法解释。
3. **数据出门。** 技能元数据加上你想塞的上下文，每次计划都要离开本机。

同类项目的实际做法：

| 项目 | 评估方式 | 链路里有 LLM 吗 |
|---|---|---|
| `pi-context-decisions` | 决策/分类模型给未露出的技能打分，每轮最多加 12 个 | 有——专用分类模型，需显式开启，文档明说延迟与费用 |
| `pi-skill-shiori` | 策略检索：只有显式标记 triggerable 的才算候选 | 无 |
| `pi-skill-router` | 每个技能集合配 routing terms 与提示词匹配 | 无 |
| `@spences10/pi-skills` | 不评估；preview → 显式确认 → 安装 | 无 |
| `pi-agent-skills` | 固定规则审批脚本执行 | 无 |

规律很清楚：**确定性闸门 + 人工确认**。没人做逐候选提示词判断。唯一用模型的那个项目，用模型回答的是"从现有库里该露出哪些"，和"这个东西要不要下载安装"是两个问题。

所以本插件按"哪一层适合什么"来切：

| 层 | 问题 | 谁做 | 理由 |
|---|---|---|---|
| 1 | 这一步需要什么能力 | 模型（步骤是它写的）+ 内置中英词表 | 语义问题——词面匹配搞不定"把这份东西变成董事会能看的东西" |
| 2 | 商店里哪个能满足、满足得多好 | 代码，量化 | 机械匹配；算术可复现、可审计 |
| 3 | 装不装 | 你 | 它会改变你的机器 |

### 打分规则

```
score(skill, step) = Σ_kw  ( 3 若 kw ∈ slug
                           + 2 若 kw ∈ name
                           + 1 若 kw ∈ description )
```

- 步骤的 token 来自**规范化能力短语**，不是步骤原文；
- 排序：`score 降序` → `下载量降序` → 步骤原文加分（封顶 6）；
- 只有命中 slug 或 name 才算有效候选，仅命中描述的视为噪声；
- 确认框里显示的数字就是这个分数，用户可以自己审。

### 这条规则暴露的三个 bug

值得记下来，因为每一个都是一类错误，而基于模型的评估会把它们藏在像模像样的说辞后面：

**1. 一个数字压过了意图。** 步骤"生成逐年 Scope 1/2/3 对比柱状图"里，token `scope` 命中了叫 `crypto-scope` 的技能——slug +3、name +2，于是它排到了所有图表技能前面。修法：候选资格只用归一后的能力短语算，步骤原文只做微调。

**2. 领域词冒充能力。** "读取 ESG 报告 PDF 并提取排放数据表格"这一步选中了 ESG **领域**技能，而不是 PDF 提取技能。修法：词表把 `esg`、`财务`、`论文` 标为 `domain`，`capabilityQuery` 优先取能力；只有在完全识别不出能力时才退回领域短语。

**3. 打分里的 off-by-one 静默丢匹配。** 原实现是 `if slug … if name … else if description`，于是同时命中 slug 和 name 的 token 得 5 分而不是 6——正好卡在默认阈值 6 上。所有单词查询（`pdf`）都被悄悄丢掉。是靠打印一个已知正确条目的分数发现的，不是靠读代码。

通用教训：**打印不出来的打分规则，就是调试不了的打分规则。** 这是把这一层留在代码里最有力的论据。

### 我没有做的

- **向量 / 语义相似度。** 能解决同义词，但需要在构建期接模型、维护向量库，而且仍然回答不了"这个技能可信吗"。第一版不值这个成本。
- **给模糊情况加 LLM 裁决。** 混合方案很诱人（确定性保召回、模型保精度）。暂缓：它会把上面三个问题重新引回到少数用例上。若将来要加，应当是可开启、有边界的，和 `pi-context-decisions` 一样。
- **可信发布者白名单。** 会让商店显得更安全，但这是产品决策、会随时间腐坏，也不属于本仓库。

## 安全阶梯

安装是这里唯一不可逆的动作，所以机制最多：

1. **黑名单** —— 下载前用 `denyPatterns` 匹配 slug/名称/描述。
2. **暂存** —— 商店装到 `~/.pi/agent/skill-autopilot/staging/<id>/`，绝不直接进技能目录。
3. **扫描** —— 读 `SKILL.md` 与随附脚本（≤40 个文件、每个 ≤200KB），匹配 19 条规则、五个等级：
   - **critical** —— 管道执行远程脚本、base64 执行、反弹 shell、`rm -rf ~`、写裸设备、读凭据文件、环境变量 + 外发请求。**自动回滚**，不弹窗，因为没有可问的余地。
   - **high** —— shell 执行、动态 eval、`chmod 777`、`sudo`、提示词注入话术（"忽略之前的指令"、"不要告诉用户"）。**二次确认**并列出命中的行；拒绝或无 UI 时丢弃。
   - **medium / low** —— 网络请求、读环境变量、全局安装、写文件、埋点。记录并在交接说明里体现。
4. **提升** —— 只有这时才把目录移进技能目录。
5. **预算** —— 按会话、按天的上限，所有路径（包括批量流水线）都受约束。
6. **日志** —— 每次检测、提议、拒绝、扫描结果、安装、失败，含规则 id。

跨行规则跑整个文件而不是逐行——第一版漏掉了 `os.environ` 与三行之后的 `requests.post` 组合。

**扫描不是什么：** 不是沙箱。它匹配文本，混淆就能绕过。它的作用是让常见情况可见、把明显破坏性的挡掉。`SECURITY.md` 把这点写明了，而不是暗示有保证。

## 已知限制

- **词表是有限的。** 识别不出能力的步骤会退化成原文匹配并抬高门槛，用召回换精度。
- **词面相关。** 与步骤措辞完全不同的技能会被漏掉，哪怕它正是对的。
- **商店检索很噪。** SkillHub 的接口对长查询严重退化，所以查询被拆成短词、并行检索、再用子串重合校验。长自然语言查询会返回热门但无关的技能。
- **只有一家商店。** `SkillStore` 接口是真的，注册表也是真的，但只实现了 SkillHub。接第二家就是实现四个方法。
- **安装延迟。** 每个技能 10–20 秒（下载 + 解压）。四步计划大约一分钟——所以它跑在显式确认和进度提示后面，而不是投机执行。

## 悬而未决

- 计划里**零候选**时，该不该告诉模型"没有对应技能"？现在是静默，风险是模型不知道已经查过。
- 被拒绝的技能要不要跨会话记住？每次重问很烦，永不重问又是错的。
- **medium** 级发现有没有更好的中间形态——在交接说明里埋一行是不是太隐蔽？
- 一步需要两种能力时（PDF *和* Excel），谁先提谁赢。多数情况对，偶尔不对。允许每步两个技能可以覆盖，代价是装得更多。
